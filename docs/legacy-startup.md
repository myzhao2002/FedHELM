# FedHELM 启动与验收说明

## 新版统一控制台（2026-09-09）

启动方式不变：双击start-training.cmd。所有模块现在共用固定侧边栏、顶栏自动处置开关、刷新与快捷操作；详情通过右侧抽屉打开。

| 导航 | 功能 |
|---|---|
| 系统总览 `/` | 关键状态卡、可点击边端拓扑、实测时延曲线、最近任务 |
| 节点与资源 `/resources` | 节点服务、模拟资源策略；进入节点后切换监控、服务、模型数据、任务和案例 |
| 故障任务 `/tasks` | 从发现到恢复的任务链；旧/history地址兼容进入此页 |
| 联邦故障记忆 `/memory` | 已验证成功案例及诊断、动作、验证数据 |
| 模型与传输 `/models` | 当前部署、模型版本库、上传与下发三个选项卡 |
| 数据存储 `/storage` | 实际文件清单、目录、文件大小、分端模型/数据/日志预览 |
| 操作日志 `/logs` | 节点/类型筛选、文本搜索、每页10/20/50/100条、上下页、页码跳转 |
| 故障注入 `/inject` | 集中的故障创建与手动恢复操作 |
| 训练与调试 `/lab` | 数据采集、训练、聚合、同步、模型路径和资源策略调整 |

模型页“当前部署”列出边缘全局模型、A/B/C端侧轻量模型，以及两个语言模型占位接口。“版本库”只展示实际日志中保存过的参数快照，按指纹去重；历史快照不等于当前运行模型。“上传与下发”可按节点和方向筛选，查看时间、方向、版本、阶段、输入输出和完整任务链。上传显示基础模型版本；下载显示接收/加载版本。无法从任务记录确定版本时显示未记录，不猜测。

“快捷操作”集中提供全端同步、全端训练、聚合；操作结果在抽屉展示并写入原有日志。仅界面与查询能力更新，自动故障处置和真实训练逻辑保持原有行为。当前仍为本机进程版。

## 新增：全过程可视化（2026-09-09）

- 首页`/`：点击A/B/C节点名称进入详情；新增实测错误率和时延曲线。
- `/node/a`、`/node/b`、`/node/c`：查看本节点服务、监控趋势、存储文件、运行模型完整参数、最近50条训练样本/本地日志预览、历史任务链及本节点成功案例。
- `/history`：查看全系统任务、训练上传/聚合下载记录、成功案例库和分页操作日志。
- `/node/edge`：查看边缘服务、全局模型及聚合等边缘操作记录。
- 每个任务可展开，查看按时间排列的实际步骤及输入输出。故障任务展示根因、置信度、模型路径、动作和恢复验证；模型任务展示训练、上传增量、回执、请求下载、参数接收、落盘加载。
- 新操作记录持久化到`runtime/training/edge/history.sqlite`，刷新和服务重启不清空。历史案例仍在memory.sqlite；本版本前未汇总的旧操作可从原节点日志查看，不伪造补齐任务链。
- 每端监控保留最近2000个采样点，图表默认展示最近180点；操作日志不按500条删除，可分页查询。图表是实际错误率、时延、连接池占用，不是CPU/GPU压力测试或伪造监控。
- 暂停自动处置仍保留观测采样，手动训练/采集正在占用操作锁时会跳过该次后台采样。
- 端侧数据预览通过UI按需读取；联邦训练只上传参数增量及评估摘要，不把原始dataset作为训练上传内容。
- 日志若遇到边缘离线，端侧记录仍写入本地events.jsonl；目前未实现离线日志自动补传，可在端详情查看本地预览。

验收脚本：`python -m scripts.verify_history`，固定测试14000端口，会注入A级服务停止并执行一轮训练/聚合/同步。结果保存`runtime/history-verification.json`。已验证同一故障任务串联、诊断数据、传输步骤、案例和端数据可查，以及重启后历史保留。

## 1. 当前能运行到哪一步

**已验证：本机独立进程版，真实测试业务故障、端侧PyTorch训练、更新上传与持久化、加权聚合、模型同步、自动诊断处置、中文状态界面。**

**尚未完成：Kubernetes集群实际部署。** Docker Desktop启动异常，WSL Docker镜像网络下载失败。K8s清单已定义边端放置规则且通过代码检查，但不能据此声称已在不同K8s节点上运行。当前A/B/C和边缘是不同程序与数据目录，共享同一台Windows电脑，无CPU/内存硬隔离。

大小语言模型按要求继续保留HTTP占位服务；后续接入API。轻量模型是160参数的小型CPU MLP，真实执行前向推理、梯度训练和参数更新，但不是论文中的完整编码器。资源/网络策略输入仍为模拟值。

## 2. 启动、打开与停止

1. 在本项目目录双击 **start-training.cmd**。
2. 等待提示10个HTTP管理/模型服务就绪，网页自动打开；另外3个业务子进程由对应控制器启动。
3. 默认地址 **http://127.0.0.1:14000/**。如端口已占用，启动器可能选备用端口，以启动窗口打印的地址为准。
4. 已有相同业务后端与训练后端的完整平台时，会打开现有平台，不重复启动一套。
5. 停止新启动的前台实例可在原启动窗口按 **Ctrl+C**。当前后台实例也可双击 **stop-training.cmd**。该脚本校验项目、PID和进程创建时间，只停止记录的项目进程树，数据保留。采集/训练/聚合进行中先等待操作结束。

关闭网页不停止后台巡检。“暂停自动处置”只暂停新处置，不停止服务；已经开始的修复会完成验证。

当前项目`.venv`及CPU PyTorch已经配置好。不要用系统默认Anaconda/Python覆盖现有虚拟环境。当前运行不需要启动Docker，也不需要GPU。

命令行等价启动方式（在项目目录运行）：

```powershell
.\.venv\Scripts\python.exe -m scripts.local --open-browser --reuse-existing --workload-backend process --training-backend torch --base-port 14000 --data-dir runtime/training
```

如复制到新机器，需要Python 3.12虚拟环境，再安装`requirements.training.txt`；该文件包含CPU PyTorch下载源，首次安装需要网络。不要使用`start-platform.cmd`验证真实训练，它保留的是旧模拟版。

| 页面 | 地址 | 用途 |
|---|---|---|
| 系统总览 | `/` | 自动调度开关、边端业务状态、13项服务清单、运行位置、数据目录、联邦接收队列、模型指纹、实际操作时间线 |
| 故障注入 | `/inject` | 选择A/B/C及故障，注入后等待自动恢复；可手动恢复测试业务 |
| 训练与调试 | `/lab` | 采集训练数据、本地训练、聚合、同步、强制模型路径与模拟网络配置 |

服务清单区分管理服务是否在线和业务是否健康。配置坏时业务进程可能仍在，但业务显示异常，这是正确行为。K8s节点名为空且显示local-process时，不能理解为已经部署K8s。

## 4. 验证真实故障

先确认总览自动处置已开启。在注入页选择节点和故障，点“注入故障”，然后观察总览。

| 故障 | 程序实际做什么 | 可观察证据 |
|---|---|---|
| 服务停止 | 结束该端控制器拥有的业务进程 | 原PID退出，故障期间业务不可用；修复生成新PID |
| 配置错误 | 写入该测试业务config.json的错误数据库开关 | 实际订单请求返回503；恢复配置后200 |
| 连接池耗尽 | 占住4个真实SQLite连接 | 实际请求等待并返回503；释放连接后200 |

这是真实的**测试工作负载故障**，不是只修改页面状态；也不是整台物理机或K8s worker宕机。进程已停止时响应码0表示连接不可用，没有伪造HTTP响应。

时间线依次展示检测、模型同步、采集、轻量诊断、模型选择、生成方案、执行、验证。只有验证成功且与注入真值一致才自动收录案例。验证使用3次HTTP观测，不是论文的完整5分钟SLO评估。

后台每轮结束后等待10秒再巡检；一次只处置一个节点。同一持续故障最多尝试两次，重试间隔至少60秒。不会注入宿主机CPU、内存、磁盘或网络故障，也不会后台自动训练。实际消耗少量CPU与内存，不能保证零开销。

## 5. 验证模型训练、上传、聚合与下发

1. 在总览暂停自动处置，以便按步骤观察实验。
2. 打开训练与调试，点“全端同步”。
3. 分别在A/B/C点“采集训练数据”，每次等待完成。采集会在对应业务逐类注入真实故障，最后恢复正常；每轮12条独立事件，8训练、4验证。
4. 点“全端训练”。每端执行60个epoch，训练在各自agent进程中完成。上传的是160维参数增量、样本量、标签直方图和验证质量，不上传原始dataset.jsonl。
5. 在总览的“联邦更新接收状态”查看A/B/C三份更新：基准版本、样本量、增量范数和已持久化状态。
6. 点“聚合更新”。必须收到本轮全部三个端的更新；成功后全局版本增加1，接收队列清空。
7. 点“全端同步”。确认三个端均显示“与全局参数一致”。比对的是完整模型内容的SHA256，不只是版本号。
8. 重新开启自动处置。

未同步的旧版本更新、同一节点同一轮的冲突更新会被拒绝。不要在同一未聚合轮次重复采集后重新训练上传不同增量；先完成现有轮次。同步采用端主动拉取，当前不是服务端主动推送。

实际验收命令（会采集、训练并注入故障，不要同时操作UI）：

```powershell
.\.venv\Scripts\python.exe -m scripts.verify_real --url http://127.0.0.1:14000 --output runtime/verified-training-storage.json
```

脚本自动暂停巡检并在退出时恢复开关，检查三份非零增量已落库、聚合参数逐项正确、三端同步指纹一致、三类故障修复成功。本次报告status=passed。

## 6. 服务应该放在哪

| 所属位置 | 服务/模块 | 实际职责 |
|---|---|---|
| 边缘 | edge | 大模型请求编排、故障记忆SQLite、资源汇总、当前原型自动巡检、UI |
| 边缘 | federation | 接收并持久化端更新、聚合全局模型 |
| 边缘 | llm-edge | 大语言模型占位API |
| A端 | agent-a、workload-a、business-a、llm-local | 端侧轻量推理与训练、选择路径、执行/验证；A端另有小模型占位API |
| B端 | agent-b、workload-b、business-b | B端轻量推理与训练及业务控制 |
| C端 | agent-c、workload-c、business-c | C端轻量推理与训练及业务控制 |

轻量模型没有搬到边缘统一推理。边缘仅做初始模型准备、汇总与聚合；每个端收到参数后在自己的agent进程中做推理/训练。

K8s清单将edge/federation/llm-edge调度到edge标签节点，将agent/workload/business放到对应A/B/C节点，llm-local只放A端。13个Deployment的安排已静态检查；集群运行验证仍未完成。后续入口`start-k8s.cmd`，详细阻塞及配置见`docs/kubernetes.md`。

## 7. 数据存储是否需要单独服务

当前不需要新增数据库服务器。SQLite是嵌入式数据库，直接由所属服务读写；独立数据目录满足此单机原型的持久化需求，减少额外内存占用。

| 数据 | 默认位置（相对项目目录） | 说明 |
|---|---|---|
| 边缘故障案例 | runtime/training/edge/memory.sqlite | 经验证案例与向量数据，SQLite内检索 |
| 待聚合更新、全局模型 | runtime/training/federation/federation.sqlite | 更新收妥后才确认持久化；全局模型推进与清空队列同一事务 |
| 全局模型导出 | runtime/training/federation/model.json | 可查看参数，数据库为已聚合模型的权威状态 |
| 每端原始训练数据 | runtime/training/agent-a/dataset.jsonl等 | 各端独立保留，不随更新上传 |
| 每端已同步模型/最近更新 | 各agent目录/model.json、last-update.json | 重启加载已同步模型；更新回执后保存最近上传内容 |
| 真实测试业务数据库和配置 | runtime/training/workload-a/business/orders.sqlite、config.json等 | A/B/C各自独立 |
| 完整运行日志 | 各服务目录/events.jsonl和runtime/training/*.log | 训练、处置、聚合的实际结果 |

当前操作日志与指标历史保存在边缘history.sqlite；总览展示最近500条，详情页可分页查看全部操作日志。每端指标保留最近2000点，模拟资源汇总仍在内存。备份时先停止平台，再复制runtime/training整个目录。

K8s目前计划使用各kind节点hostPath，Pod重建可保留，删除整个kind集群会丢失；尚未实现生产级共享存储、高可用数据库或跨节点迁移。

## 8. 论文自动化与手动控制的区别

依据FedHELM-cn.pdf：PDF第7页§3.1规定端侧感知、诊断、本地训练及处置；PDF第8页§3.2明确“并在端侧自动执行”，成功判定包含“无人工干预”；§4.3及算法1是事件级自动模式选择，算法2描述端侧训练、上传和聚合。

因此论文主闭环是自动的，并非每次故障都要人按诊断和修复按钮。但这不等于不能人工配置实验：故障注入、策略阈值、资源条件和实验启停都可人为设置。原文未要求我们这个UI，也未明确规定每个动作都要人工审批。

本原型提供的暂停、强制模型路径、手动恢复和手动训练是工程调试能力。强制路径属于对照实验，手动恢复不能统计为论文自动恢复成功。当前训练轮次由人触发以控制资源开销；资源感知策略、模型规模、聚合公式、验证窗口、样本规模等仍与论文有差异，不能声称完整复现。

## 9. 常见问题

- 页面打不开：看启动窗口或runtime/training-launch-error.log；确认使用窗口打印端口。不要用旧9000页面判断新功能。
- 返回409“另一个操作正在执行”：等待当前巡检/训练结束再点；需要固定步骤时先暂停自动处置。
- 模型显示未同步：全端同步后再看指纹；不能用页面版本相同代替参数核验。
- 自动修复两次后停止：查看时间线错误、服务在线状态，可手动恢复测试业务；不做无限重启。
- 模型/案例数据不见：检查启动时的data-dir和页面“查看存储”，不同启动模式的数据目录不同。
- K8s打不开：当前尚未部署成功，不影响本机进程版使用；不要重置或删除电脑上其他Docker环境的数据。


## 10. 新增论文故障与进度条

故障注入页列出论文十类故障，目前五类支持真实注入，新增线程池耗尽与依赖超时。点击注入后直接打开七阶段进度，显示毫秒时间、耗时、诊断来源、修复动作、HTTP 验证及案例收录，并自动刷新。新增两类使用显式日志规则，原四分类轻量模型的训练上传链路保留；其余五类等待隔离环境。详细机制和边界见 [故障注入与任务进度](docs/fault-injection.md)。

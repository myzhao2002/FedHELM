# 自动监控与可视化操作

启动：`start-training.cmd`。本机当前运行地址为 http://127.0.0.1:14000/ 。

## 三个页面

- `/`：系统总览，显示边缘服务、A/B/C端状态、业务PID或Pod、实际错误率与时延、轻量模型版本、调度状态及操作时间线。
- `/inject`：独立故障注入页，只需选择节点和故障，再点注入。不必再点诊断、修复或案例提交。
- `/lab`：保留原训练、资源模拟及手动接口调试工作台。需要逐步手动演示时，先在总览暂停自动处置。

## 后台逻辑

边缘进程中的单个调度线程在一轮结束10秒后巡检。逐个调用A/B/C测试业务观测接口，发现不健康或错误率大于5%后，同步全局模型和故障记忆，再调用端节点自动处置流程。关闭浏览器不影响后台巡检。仅启动一个边缘服务实例/worker；当前未实现跨副本选主。

模型选择沿用现有策略：低置信度（小于55%）升级边缘大模型；A级且内存策略值不少于1024MB、RTT策略值大于100ms时选本地小模型；其他高置信度情况走轻量模型加处置模板/成功案例。资源和网络策略输入仍为模拟值；大小语言模型仍为占位服务。

执行修复后，验证3次实际HTTP观测的健康、错误率和时延。恢复成功且诊断与本次注入真值相符，才自动收录案例。系统自然检测到但没有注入真值的故障可以尝试修复，不自动声称根因已确认。

时间线按实际步骤追加：注入、检测、模型同步、采集、轻量诊断、模型选择、生成方案、执行、验证和案例入库。记录关联端节点及事件ID，总览展示最近500条，完整操作日志保存到history.sqlite，边缘进程重启后可继续查询；完整端节点运行结果仍保存在各端events.jsonl中。

## 资源与操作约束

- 不使用GPU，不自动采集训练集或训练模型。
- 同时最多处理一个节点；与控制台注入、采集、训练共享互斥锁，忙时操作返回409，避免互相干扰。直接调用端节点API的外部程序需要自行协调。
- 同一持续故障最多尝试两次，两次之间至少60秒，之后等待人工检查。重新注入或观测恢复会重置次数。
- 暂停只阻止新处置，已开始的修复完成验证。暂停设置仅本次进程有效；可设置`AUTO_MONITOR=0`让下次启动默认暂停。
- 仅作用于本项目业务进程/业务Deployment、测试配置及SQLite池，不修改宿主机网络、驱动、系统服务或其他应用。
- 本机运行仍是process后端。Kubernetes部署状态与阻塞见kubernetes.md，不能把这里的验证当成Kubernetes验证。

## 接口

| 接口 | 功能 |
|---|---|
| GET /ui/monitor | 自动开关、巡检状态、最近事件 |
| PUT /ui/monitor | JSON `{"enabled":true}` 启用，false暂停 |
| POST /ui/events | 端节点回报实际步骤，含node/event_id/stage/detail |
| POST /ui/command | 故障注入和原有操作，注入后后台自动接管 |

验证：26项测试通过。浏览器实际注入A级服务停止后自动恢复并入库；B配置错误、C连接池耗尽的自动恢复及暂停保持故障验证通过。报告`runtime/monitor-verification.json`，复验命令`python -m scripts.verify_monitor`（会操作本机14000端口的测试业务）。原有手动验证脚本verify_real运行前应暂停自动监控，结束后再开启；local --demo已自动禁用巡检。
